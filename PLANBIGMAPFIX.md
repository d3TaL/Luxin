# План исправления отслеживания большой карты (свайпы и зумы)

Дата: 2026-11-24. Ветка: `feat/bigmap-detection-fix-sonnet`.

## 1. Диагноз (по коду)

Текущая схема (`tracker/src/bigmap_session.cpp`):
- Первичная привязка: `registerBigMap` — SIFT (12000 точек, 1440p) по всем эталонам, 1,5–2,4 с,
  только на неподвижной карте (2 кадра + 0,5 с), не чаще раза в 2 с.
- Сопровождение: ORB (1200) + BFMatcher knn каждый кадр против ОДНОГО фиксированного опорного
  кадра (720p, 1560×720). Гейты: matches/inliers ≥24, ratio ≥0,65, overlap ≥20%,
  scale 0,7–1,4, rotation ≤1°, dense_change/tile_change, контрольные ROI.
- Опора живёт 10 с; renew() в 6–8 с не принимается, если карта двигалась.
- Цикл 67 мс (цель 15 fps), фактически ~6 fps. Оверлей рисует позу устаревшего кадра.

Почему ломаются свайпы/зумы:
1. Фиксированный якорь: длинный свайп убивает перекрытие, зум >1,4 — scale_bounds.
   3 неудачи → сброс → ожидание неподвижности → SIFT. Итого 3–5 с без привязки.
2. Пиксельные гейты сравнивают с «копией якоря» и срабатывают на нормальное движение
   (подгрузка LOD тайлов, смаз). `appearance_tolerated` — обход, не решение.
3. Иконки игры не масштабируются при зуме → их ORB-точки ломают модель масштаба.
4. Дорогой шаг (ORB detect + BF 1200×1200 + warp + гейты на 1560×720) → низкий fps →
   большие шаги между кадрами (150–400 px, зум 12–20% за кадр) → ещё больше срывов.
5. Нет предсказания/экстраполяции → метки отстают от пальца на 100–200 мс.
6. Модель 4-DOF с отбраковкой поворота, хотя карта не вращается (нужно 3-DOF: s, tx, ty).

## 2. Целевая архитектура

Разделить быстрое слежение и медленную проверку (как tracking/relocalization в SLAM):

| Поток | Частота | Что делает |
|---|---|---|
| Слежение | каждый кадр | LK-поток (Shi-Tomasi 150–300 точек, ~360p, forward-backward check) кадр→предыдущий кадр; RANSAC 3-DOF (s, tx, ty); накопление позы от последнего ключевого кадра; фильтр α-β/Калман по (tx, ty, log s); публикация с экстраполяцией на момент показа |
| Сверка с эталоном | 2–5 Гц, фоном | По предсказанной позе вырезать кусок эталона с запасом в текущем масштабе, локально сопоставить (ORB/SIFT на фрагменте, затем ECC). Мягкая коррекция дрейфа, проверка пространства, смена ключевого кадра |
| Релокализация | только при потере | Глобальный `registerBigMap`, сначала в окрестности последней позы; не требовать полной неподвижности |

Детали:
- Ключевой кадр меняется при перекрытии <~50% или изменении масштаба >1,5×, только если
  текущая поза недавно подтверждена сверкой с эталоном.
- Срок «10 с от якоря» заменяется на «время с последней успешной сверки с эталоном».
- Коррекция от фоновой сверки: разница между абсолютной позой снимка и накопленной позой
  НА ТОТ ЖЕ timestamp (хранить историю поз по timestamp), применять плавно.
- Иконки игры исключать из точек (маска по цвету/шаблонам или хотя бы по рамкам).
- Пиксельные гейты не решают публикацию во время движения. Контрольные ROI остаются как
  детектор смены экрана (панель, меню, этаж).
- Фазовая корреляция — только запасной вариант для малых сдвигов на бедной текстуре.
  Фурье–Меллин не использовать (нестабилен при разной мягкости кадров).
- Захват: VirtualDisplay в половинном разрешении — меньше копирований, трекеру хватает.
- При потере: метки скрыть, позу не забывать, релокализация с приором.
- Осознанно пересматривается инвариант C5 из `research/bigmap_tracking_v2.md`
  (запрет цепочки накапливающихся преобразований): дрейф ограничивается сверкой с эталоном.

Риски: дрейф на реальных кадрах (LOD, смаз), ложные совпадения на повторяющейся текстуре,
время шага на телефоне. Поэтому сначала данные и офлайн-сравнение, потом нативный код.

## 3. Этапы

### Этап 1 — Диагностический дамп кадров (Android)
Цель: реальные последовательности соседних кадров для офлайн-оценки.
- Переключатель «Дамп кадров большой карты» в UI (рядом с карточкой экспорта логов,
  `diagnostics/DiagnosticLogExportCard.kt`), по умолчанию выключен.
- Писать в папку, уже выбранную для экспорта логов (SAF tree URI из
  `DiagnosticLogExporter.loadDestination`), подпапка `bigmap_dump_<дата-время>/`.
- Сохранять кадры С ЧАСТОТОЙ ЗАХВАТА, а не трекера: отдельный путь чтения из ImageReader
  или очередь в фоновом писателе, не блокирующая цикл слежения. Если кадр не успели
  записать — пропускать (bounded queue, drop oldest) и считать пропуски.
- Формат: PNG, исходное разрешение, цвет (RGBA→PNG). Имя `f_<index>_<timestampNs>.png`.
- `frames.csv`: index, timestampNs, width, height, generation, screenMode (если известен),
  dropped_before.
- Ограничение: длительность (например 20 с) или N кадров (например 400), авто-стоп.
- Сохранить вместе с дампом отфильтрованный трекинг-лог (переиспользовать экспортёр).
- Ничего не менять в логике трекинга и публикации.
- Unit-тесты на чистую логику (именование, CSV, bounded queue/drop).

Сценарии записи (для пользователя): длинный свайп с инерцией; щипок в обе стороны с
переходом LOD; свайп над морем/равниной; открытие панели посреди движения; смена этажа.

Быстрая альтернатива без кода: `scrcpy --record` с высоким битрейтом (сжатие портит мелкую
текстуру — окончательные выводы только по PNG).

Использование (реализовано, двухфазный RAM-burst):
1. В карточке «Логи трекинга» выбрать папку SAF (например `Download/LuxinLogs`).
2. Запустить захват экрана (раздел 3) и при желании трекер.
3. В карточке «Дамп кадров большой карты» включить переключатель: после обратного отсчёта (5 с на переход в игру) кадры пишутся в заранее выделенный буфер до 64 МиБ без кодирования на лету. Разрешение — до 720p, запись — в градациях серого плюс каждый 30-й кадр в цвете. Размер буфера и разрешение выбираются по доступной памяти процесса: берётся первое разрешение из 720/540/360p, при котором в буфер влезает не меньше 150 кадров (≈3 с при ~47 fps), обычно это 360p; при ошибке выделения пробуется буфер меньшего размера. Реальные дампы 26.11 при прежних настройках (540p, каждый 10-й кадр в цвете) вмещали лишь 60–62 кадра (≈1,3 с), и жест зума обрывался. Автостоп: заполнение буфера или 20 с (либо выключение переключателя).
4. После остановки записи в фоне кодируются `f_<index>_<timestampNs>.png`, `c_<index>_<timestampNs>.png` (ключевые цветные), `frames.csv`, `summary.txt` (fps, max gap, пропуски) и отфильтрованный трекинг-лог в подпапку `bigmap_dump_<ГГГГММДД_ЧЧММСС>/`.

### Этап 2 — Офлайн-сравнение методов (`spike/`)
Скрипт `spike/bigmap_motion_eval.py` (+ тесты на синтетике `spike/test_bigmap_motion_eval.py`):
- Вход: папка дампа (PNG + frames.csv) или видео (через существующий `video_frames.py`).
- Предобработка: серый, ресайз к рабочей высоте (параметр: 720 / 360), маска UI —
  портировать `bigMapGeometryMask` (рамки в координатах 3120×1440).
- Методы кадр→предыдущий кадр:
  1. ORB + BF knn + ratio 0,75 + estimateAffinePartial2D (как сейчас, но к предыдущему кадру);
  2. LK pyramidal + forward-backward check + RANSAC 3-DOF (s, tx, ty);
  3. фазовая корреляция (только сдвиг) — для справки;
  4. текущая схема «фиксированный якорь» (ORB к первому кадру с переякорением при срыве)
     — базовая линия.
- Опционально: предсказание по постоянной скорости как начальное приближение для LK.
- Эталонные позы: опционально (флаг) — абсолютная поза на каждом кадре через
  desktop-бинарь трекера (`tracker/tests/bigmap_geometry_frames.cpp`, если подходит),
  иначе — по ORB/SIFT к далёкому кадру с высоким качеством. Если эталона нет —
  метрики самосогласованности: ошибка замыкания (A→B→C vs A→C), forward-backward.
- Метрики: доля успешных шагов, время на шаг (мс), накопленный дрейф (px в 3120-шкале)
  на длине цепочки, максимальный «провал» без позы, масштаб/сдвиг по кадрам.
- Выход: CSV по кадрам + сводка в stdout + (опционально) PNG-графики траекторий.
- Зависимости: numpy, opencv-python-headless (в venv, не системно).

Запуск (реализовано):
- Дамп: `/tmp/opencode/luxin-venv/bin/python -I spike/bigmap_motion_eval.py <папка_дампа> --work-height 360 --lk-predict --gt-sift --out-csv eval.csv --plot traj.png`
- Видео: `/tmp/opencode/luxin-venv/bin/python -I spike/bigmap_motion_eval.py <видео.mp4> --pts --work-height 360 --lk-predict --out-csv eval.csv`
- Тесты на синтетике: `/tmp/opencode/luxin-venv/bin/python -I spike/test_bigmap_motion_eval.py -v`
