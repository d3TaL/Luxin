# Интерактивная карта Genshin с оверлеем (Android)

Статус: проект, до первого Android-прототипа. CV-спайк проверен на скриншотах и записи экрана
(раздел «Проверка распознавания»). Расчёты выполняются в Linux/PRoot на самом телефоне
Samsung SM-S938B, но офлайн: захват, оверлей и работа трекера одновременно с игрой ещё не проверены.

## Цель

Личное приложение (не для публикации): интерактивная карта с метками плюс оверлей поверх игры,
который показывает те же метки на большой карте и на миникарте синхронно с игрой.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Аудитория | Только для себя, Android 14+, флагман |
| Подход к синхронизации | Пассивный: захват экрана + CV. Без памяти, инъекций, автоматизации ввода |
| Захват | MediaProjection по умолчанию; Shizuku и AccessibilityService — опциональные режимы |
| Данные | Kongying Tavern. Собственный формат пользователя пока не подключаем |
| Касания | Гибрид: оверлей прозрачен для касаний, плавающая кнопка включает режим редактирования |
| Функции v1 | Отметка собранного, фильтры и поиск, цель «ближайшая метка», бэкап файлом |
| Маршруты | Нет. Цель — ближайшая несобранная метка: лёгкая подсветка и стрелка к ней |
| Пространства и уровни | Закладываются в модель и трекер с самого начала (см. раздел ниже) |
| Синхронизация | Экспорт/импорт одного файла. Бэкенда нет |
| Сборка | GitHub Actions (локальная среда — PRoot на arm64, SDK/NDK там не собирают) |

## Стек

| Слой | Выбор |
|---|---|
| Язык, UI | Kotlin, Jetpack Compose, корутины/Flow |
| Карта в приложении | MapCompose (тайловая не-гео карта с метками) |

## Модули

```
:app        Compose UI: карта, фильтры, поиск, настройки, бэкап
:data       Room, модель, загрузка Kongying, прогресс
:capture    FrameSource и три реализации
:tracking   JNI-обёртка над C++ трекером
:overlay    Сервис, окна, отрисовка меток и указателя
tracker/    C++ библиотека без зависимостей от Android + desktop-стенд
```

`tracker/` собирается и под Android (через NDK), и под Linux — чтобы отлаживать распознавание
на записанных скриншотах без телефона и гонять это же в CI.

## Пространства и уровни

Карта в игре не одна плоскость. Это учтено в модели данных, в трекере и в правилах показа.

- **Пространство** — отдельная карта со своей системой координат и своей рисовкой (основной
  Тейват, отдельные карты вроде «Храма пространства»). У каждого пространства свой эталон
  и свой индекс для распознавания.
- **Уровень** — слой внутри пространства поверх или под поверхностью (например «Верхний уровень
  канала талых вод»). Уровни сгруппированы по местности: переключатель на большой карте
  показывает только уровни той группы, над которой находится центр экрана.

Позиция и активный уровень определяются независимо:

- `PositionFix { space, transform, geometryQuality }` — абсолютная привязка по всей доступной
  геометрии, включая приглушённые соседние этажи.
- `LayerDecision { layerId | surface | unknown, status, appearanceQuality }` — активный этаж
  при уже фиксированной позиции. Неизвестный уровень **не** означает поверхность.
- `TrackingState { position: PositionFix?, layer: LayerDecision }` сохраняет позицию, даже если
  этаж не определён. `MapFix` для отрисовки меток получается только при уверенной позиции
  и подтверждённом уровне; иначе метки/цель соответствующего слоя не показываются.

У отметки `Marker` пустой уровень по-прежнему означает поверхность; это отдельное понятие
от `unknown` в состоянии распознавания. Для большой карты без известного этажа можно
показать положение игрока, но нельзя самовольно выбрать набор меток.

Как это устроено в данных Kongying (подробно — `research/kongying.md`):

- **Пространство = набор тайлов.** Их 11: `twt702` — весь открытый Тейват одной картой
  (включая Натлан, Нод-Край и Снежную) и 10 отдельных: `kzsd2` («Храм пространства»), `cyjy`,
  `yxg`, `jrzh`, `ygss`, `moon2`, `lxsj`, `xmlk`, `qd1`, `qd28`. Что `kzsd2` — это «Храм
  пространства», подтверждено наложением скриншотов.
- **У метки нет поля пространства.** Цепочка: первый предмет метки → область предмета → набор
  тайлов области. Координаты разных пространств пересекаются, поэтому без этой цепочки метки
  смешивать нельзя.
- **Уровень = значение из `extra.underground.region_levels`** метки (например
  `SNOWMELT_DRAINAGE_CHANNEL_UG1`). Те же значения стоят в конфиге области вместе с группой
  уровней, изображениями уровня и их границами в координатах меток. Изображения уровней —
  0.75 px на единицу координат, их нужно растягивать по границам.
- Уровни расписаны для 26 областей (462 изображения). В 9 старых областях у метки есть только
  признак «не на поверхности» без конкретного уровня; такие метки показываем на любом уровне
  этой местности, приглушённо.
- Сайт Kongying метки по уровням не фильтрует — это делает приложение.

### Как это выглядит в игре (по скриншотам 3120×1440)

Миникарта:

- три вида содержимого: поверхность; уровень (яркий фрагмент уровня на тёмной полупрозрачной
  подложке); пусто (интерьеры — только кольцо, «N» и стрелка игрока);
- уровень на миникарте игра выбирает сама — тот, на котором стоит персонаж.

Большая карта:

- справа колонка кнопок уровней: кнопка поверхности и 1–3 кнопки уровней. Порядок в колонке
  отражает высоту: уровни над землёй стоят выше кнопки поверхности, подземные — ниже.
  Выбранная кнопка подсвечена, значок человечка отмечает уровень игрока, рядом с выбранной
  кнопкой всплывает название уровня;
- при выбранном уровне поверхность сильно затемнена, ярким остаётся только фрагмент уровня;
- колонка сдвигается влево, когда открыта боковая панель метки (панель закрывает ~30% экрана);
- слева ползунок масштаба: положение бегунка даёт начальную оценку масштаба;
- справа внизу — название области; у иконок телепортов, стоящих на уровнях, значок слоёв:
  синий — телепорт выбранного уровня, серый — другого;
- только что открытая карта центрирована на игроке: стрелка стоит в центре экрана.

### Определение пространства

- Трекер помнит текущее пространство. При потере сначала ищет в нём, потом в остальных
  по давности посещения.
- На большой карте пользователь может листать другие пространства, поэтому там поиск идёт
  по грубым (уменьшенным) индексам всех пространств сразу — они маленькие.
- Ручной выбор пространства в плавающей панели остаётся как запасной путь.

### Определение уровня

- Миникарта: доля тёмной подложки — подсказка, а не жёсткий классификатор уровня: крупные
  открытые уровни выглядят как поверхность. Кандидаты — поверхность и уровни, чьи границы
  накрывают последнюю известную позицию (с запасом на движение); фрагмент сопоставляется
  с каждым. Уровень принимается только при достаточном качестве и отрыве от альтернатив.
  Если поверхность и уровень имеют одинаковую рисовку, одного изображения недостаточно:
  сохраняется предыдущая гипотеза / подсказка с большой карты, либо уровень остаётся неизвестным.
  Пустая миникарта и неоднозначная позиция не дают права продолжать показ меток.
- Большая карта: читается колонка кнопок (какая подсвечена и где она относительно кнопки
  поверхности); группа уровней берётся по центру экрана; результат перепроверяется сопоставлением
  яркого фрагмента с изображением уровня.
- Положение на затемнённой карте определяется по яркому фрагменту уровня, эталон — изображение
  уровня из Kongying. Проверено: по затемнённой поверхности маленький уровень даёт 6 совпадений
  (ненадёжно), по изображению уровня — 65. Попутно это подтверждает сам уровень: совпало
  изображение — значит, выбран он.
- Крупные «открытые» уровни Kongying уже нарисовал в базовых тайлах (пример — «городок под
  крыльями» в Снежной), там положение находится и по базовой карте.

### Правила показа меток

- Показываются метки отображаемого уровня: на большой карте — выбранного, на миникарте — текущего.
- Метки других уровней по настройке либо скрыты, либо приглушены и помечены значком слоёв,
  как это делает сама игра с телепортами.
- В пустом состоянии миникарты оверлей скрыт.

## Синхронизация с игрой

### Состояния

Каждый кадр относится к одному из трёх состояний, определяется дешёвыми шаблонами фиксированных
элементов UI:

1. геймплей с миникартой — режим миникарты;
2. открыта большая карта — режим большой карты;
3. всё остальное (меню, диалоги, катсцены, игра не на переднем плане) — оверлей скрыт.

### Миникарта

Требование к игре: Settings → Other → Mini-Map → **Fixed** (север сверху). Тогда поворота нет,
ищется сдвиг и масштаб; между устойчивыми масштабами возможна анимация.

Измеренные устойчивые масштабы (px миникарты на единицу координат Kongying при высоте
кадра 1440; для другой высоты умножаются на `H / 1440`):

| Масштаб | Радиус обзора | Где измерен |
|---|---|---|
| ×1 = 0.75 | 235 ед. | луга Мондштадта, открытая часть уровня `WING_SHADOWED_TOWN` в Снежной |
| ×2 = 1.50 | 117 ед. | подземный уровень в Снежной; `SNOWMELT_DRAINAGE_CHANNEL_UG1` на записи |
| ×3 = 2.25 | 78 ед. | Кур-де-Фонтейн, Мондштадт (город), вход в деревню Окурово |

В записи 2340×1080 это 0.5625 / 1.125 / 1.6875 px/ед. Для ×1 и ×3 независимая оценка SIFT
подтверждает эти значения с точностью примерно до тысячных px/ед. Наблюдение: поселения
приближаются до ×3, открытая местность использует ×1. Но признак уровня Kongying не задаёт
масштаб: крупный «подземный» `WING_SHADOWED_TOWN` в игре выглядит как открытая карта и тоже
использует ×1. Универсальное правило и полный список масштабов не установлены; трекер
определяет масштаб по изображению, а не по типу местности.

**Переход масштаба анимирован.** При входе в Окурово (177.51–178.14 с записи) масштаб почти
линейно меняется с ×1 до ×3 за ~0.63 с. Поиск по непрерывной сетке масштабов сохраняет позицию
и корреляцию 0.57–0.82; перебор только трёх устойчивых значений даёт слабые кадры и краткий
ложный режим «×2». В основном трекере: устойчивые значения — быстрый путь; при падении качества
или признаке изменения масштаба — локальный поиск также по масштабу. Если уверенной оценки
нет, метки скрываются, а не рисуются в неверном масштабе. Такой переход пока исследован
отдельным `zoom_probe.py`, в дискретный видеотрекер ещё не встроен.

Измерено на скриншотах 3120×1440: центр кольца (399.5, 207.5), радиус 176 px (0.122 высоты
экрана), положение одинаково во всех кадрах. На другом устройстве кольцо находится тем же
способом автоматически (`spike/measure_minimap.py`): усреднение градиентов по нескольким кадрам
и подгонка окружности.

Что мешает сопоставлению и как это учитывается:

- миникарта полупрозрачна, сцена просвечивает, сильнее к краям — сравнение по градиентам
  или нормированной корреляции, центр весит больше краёв;
- статичные перекрытия (иконка Паймон, «N», значок заданий) — постоянная маска;
- стрелка игрока, конус обзора, иконки телепортов и заданий — динамическая маска;
- однотонные участки (вода, туман) — сопровождение по инерции до появления деталей.

Алгоритм:

- Затравка: позиция стрелки игрока на большой карте. Большая карта распознаётся надёжно
  (тысячи совпадений), и игрок открывает её часто, поэтому это основной способ узнать, где искать.
  При выборе телепорта можно запомнить его координаты и уровень: после загрузки это более
  полезная затравка, чем последняя позиция до телепортации. На записи выбранный телепорт
  совпал с точкой Kongying 121707 уровня `SNOWMELT_DRAINAGE_CHANNEL_UG1`; распознавание
  самого выбора телепорта в трекере ещё не реализовано.
- Первый спайк сопровождения: masked zero-mean NCC по градиентам в окрестности последней
  позиции, по устойчивым масштабам. Для основного трекера нужен также поиск масштаба во время
  анимации. Другие уровни, покрывающие позицию, перепроверяются периодически и при падении
  качества, а не на каждом кадре; переход — с гистерезисом.
- SIFT-адаптация политики cvAutoTrack: глобальный захват → локальный поиск → повторный
  глобальный после трёх отказов, непрерывный масштаб и подтверждение захвата двумя кадрами.
  Первый вариант смешивал положение и этаж и почти всё отклонял; сохранён как baseline.
- В разделённом варианте `spike/split_tracker.py` позиция находится по геометрии всей сцены,
  а покрытие нормируется по видимому контексту, не по полному кольцу. Уровень выбирается
  отдельно при одной фиксированной геометрии по видимым различающим фрагментам alpha-масок,
  с устойчивой коррекцией яркости. Большие соседние этажи не должны подавлять маленький.
  Неоднозначный этаж не сбрасывает позицию, но запрещает показ его меток. Новый этаж требует
  двух последовательных согласованных наблюдений; старый слой при неуверенности не выдаётся.
  На пользовательских интервалах все 94 оценённых кадра имеют позицию, этаж верен в 88,
  есть 2 расхождения около переходов и 4 отказа. Это запись разработки, не доказательство
  точности на новых данных; абсолютная ошибка координат не измерена.
  Подробности — `research/channel_layers.md`, происхождение — `research/cvautotrack.md`,
  MIT-notice — `THIRD_PARTY_NOTICES.md`. Старые спайки остаются для сравнения.
- Для NCC нужен нижний порог дисперсии эталона. На однотонной тёмной подложке уровней
  `cv2.matchTemplate(TM_CCOEFF_NORMED, mask=...)` выдавал численно ложные пики до ~0.6.
  В спайке использована явная корреляция с ограничением дисперсии снизу (0.25 от стандартного
  отклонения шаблона); пустые участки перестают конкурировать с текстурой уровня.
- Захват позиции требует не только высокого пика, но и отличия от альтернативных мест,
  согласованности координат, масштаба и уровня на нескольких кадрах. В спайке пороги
  усилены до acquire ≥ 0.50, second ≤ 0.60 × peak, keep ≥ 0.40: старые 0.40 / 0.80 / 0.30
  принимали неверные уровни, когда нужного эталона не было. Эти числа подобраны на одной
  записи и не являются универсальными; сравнение конкурирующих уровней и подтверждение
  захвата несколькими кадрами пока остаются требованиями к основному трекеру.
- Глобальный поиск без затравки — запасной путь. В спайке проверены NCC по нескольким локальным
  эталонам и feature matching кропа миникарты. NCC по всему миру слишком дорог, а SIFT
  в городском масштабе дал всего 7–8 совпадений на участке 2816×2816 единиц — нужен
  иерархический поиск с ограничением кандидатов по пространству, последней позиции и телепортам.
- Захват в пониженном разрешении, частота трекинга адаптивная; оверлей интерполирует между
  уверенными оценками только короткое время, при потере метки скрывает.

### Большая карта

Карта только сдвигается и масштабируется, поэтому ищется преобразование из 3 параметров:
feature matching скриншота с эталоном, затем RANSAC (`estimateAffinePartial2D`).
Бегунок масштаба слева даёт начальную оценку масштаба и сужает поиск.
Пока карта движется (определяется по разнице кадров), метки скрыты; после остановки — показаны.

Проверено на шести скриншотах: масштаб от 0.54 до 2.33 px на единицу, поворот 0°, телепорты
Kongying после преобразования попадают на иконки игры. Облака поверх карты («Храм
пространства») и открытая боковая панель не помешали.

Маска UI: баннер и список слева вверху, ползунок масштаба, панель ресурсов и кнопка закрытия
сверху, колонка уровней справа, подпись области справа внизу, боковая панель метки, если открыта.

Запасной вариант, если матчинг по текстуре окажется ненадёжным: искать на скриншоте иконки
телепортов и статуй и сопоставлять их созвездие с известными координатами.

## Оверлей

- Полноэкранное окно: `FLAG_NOT_TOUCHABLE | FLAG_NOT_FOCUSABLE | FLAG_LAYOUT_NO_LIMITS`,
  вырез экрана включён в раскладку, чтобы координаты совпадали с захватом.
- Тип окна `TYPE_APPLICATION_OVERLAY` требует alpha ≤ 0.8, иначе Android 12+ блокирует касания
  сквозь него. Если включена служба Accessibility, используется `TYPE_ACCESSIBILITY_OVERLAY`
  без этого ограничения.
- Плавающая кнопка — отдельное маленькое окно. Она включает режим редактирования: окно меток
  становится касаемым, тап выбирает ближайшую метку (отметить собранной, описание).
  В этом режиме игра касаний не получает.
- Миникарта: метки в радиусе обзора, обрезка по кругу.

### Цель — ближайшая метка

Заранее заданного порядка точек нет.

- Цель — ближайшая к игроку несобранная метка из активных фильтров. Пересчитывается при движении;
  смена цели с гистерезисом, чтобы указатель не прыгал между двумя равноудалёнными метками.
- Сначала рассматриваются метки текущего уровня. Метка другого уровня может стать целью только
  если на текущем ничего нет; тогда она помечена значком слоёв.
- Цель слегка подсвечена (мягкое кольцо вокруг иконки) и на миникарте, и на большой карте.
- Если цель за пределами круга миникарты — небольшая стрелка на ободе в её направлении
  и расстояние.
- Кнопки «отметить собранным» и «пропустить» — в плавающей панели; после отметки целью становится
  следующая ближайшая.

## Данные

Модель:

- `Space` — пространство: своя система координат, набор тайлов, эталон для распознавания.
- `Layer` — уровень внутри пространства: название, группа, порядок по высоте, изображение
  и его границы в координатах пространства.
- `Category` — тип метки, иконка.
- `Marker` — `(source, sourceId)` как ключ, категория, пространство, уровень (пусто = поверхность),
  координаты в системе пространства, название, описание, картинка.
- `Progress` — ключ метки, время отметки.

Каноническая система координат — координаты меток Kongying внутри пространства: 1 единица =
1 px тайла максимального масштаба (z=13), x вправо, y вниз. Она же используется в CV, поэтому
метка переводится на экран одним преобразованием, полученным от трекера.

Ключ `(source, sourceId)` оставлен, хотя источник пока один: прогресс должен пережить обновления
данных и возможное подключение второго источника.

Источник — Kongying Tavern. Адреса, форматы и примеры запросов — в `research/kongying.md`,
доступ проверен живыми запросами:

- API `https://cloud.yuanshen.site/api/…`. Гостевой токен выдаётся по публичной паре клиента
  из их же фронтенда, живёт 30 минут, обновляется повторным запросом.
- Метки — 46 чанков gzip-JSON с индексом md5: при обновлении скачиваются только изменившиеся.
  Всего 131 тыс. меток, 5 130 предметов, 1 194 иконки, 48 областей.
- Конфиг (`assets.yuanshen.site/system.json.bz2`): наборы тайлов, уровни, изображения уровней.
- Тайлы: `assets.yuanshen.site/tiles_<код>/<z>/<x>_<y>`, 256 px, z 10–13. Набор разреженный
  (404 = пустой тайл), формат определяется по содержимому, а не по расширению.
- В ответах есть блок `users` с личными данными авторов меток — его не сохраняем.
- Все названия только на упрощённом китайском. Для интерфейса нужен свой перевод категорий;
  откуда его взять, не решено.
- Ограничений частоты запросов не замечено, но это чужой некоммерческий сервер: данные
  и тайлы кэшируются на устройстве, обновление — по кнопке или не чаще раза в день.
- Условия использования данных не проверялись; для личного приложения это не препятствие,
  для публикации — нужно проверить.

Объём (131 тыс. меток) помещается в память; выборка по видимой области — простая сетка.

## Риски

1. **Оверлей попадает в собственный захват** и портит распознавание. Варианты: MediaProjection
   в режиме «одно приложение»; `takeScreenshotOfWindow` (API 34) из AccessibilityService;
   маскирование пикселей, которые мы сами нарисовали (работает всегда, остаётся как fallback).
   Что первые два исключают оверлей — не проверено.
2. **Качество трекинга миникарты**: движение в городе и по мало́детальным лугам проверено
   на записи, но вода, почти однотонные участки и другие настройки UI ещё нет. Известны три
   устойчивых масштаба и плавный переход ×1→×3; полный список и правило выбора неизвестны.
   Ошибочный уровень может дать правдоподобный пик: обязательны отказ при неоднозначности
   и проверка захвата несколькими кадрами.
3. **Соответствие эталона игре**: в проверенных местах (Фонтейн, Мондштадт, Снежная, «Храм
   пространства») рисовка совпадает до долей единицы. Остаётся задержка появления новых регионов
   у Kongying.
4. **Зависимость от Kongying**: доступ сейчас работает без регистрации, но это неофициальный
   для нас API — адреса и формат могут измениться без предупреждения. Смягчение: локальный кэш,
   приложение работает на последних скачанных данных.
5. **Нагрев и FPS** рядом с игрой.
6. **Лимит частоты скриншотов через Accessibility**: существует, значение не проверено.
7. **Аккаунт**: подход пассивный, но сторонние инструменты формально запрещены ToS.

### Запись экрана

Запись 2340×1080, ~30.145 fps, 183.4 с: Мондштадт → телепортация к статуе → луга → большая
карта и выбор подземного телепорта в Снежной → подземелье → выход и вход в деревню Окурово.
Трекер обрабатывает 10 кадров на секунду видео офлайн; это частота выборки, **не достигнутая
скорость реального времени**. Все материалы с UID, скачанные эталоны и результаты остаются
локально, вне Git.

Подтверждённые участки сопровождения:

| Время записи | Место / эталон | Масштаб | Кадров с позицией | Корреляция, средняя / минимум |
|---|---|---|---|---|
| 0.00–14.73 с | Мондштадт | ×3 | 148 | 0.66 / 0.58 |
| 22.33–39.61 с | луга Мондштадта | ×1 | 174 | 0.59 / 0.51 |
| 72.02–109.01 с | `SNOWMELT_DRAINAGE_CHANNEL_UG1` | ×2 | 38 (выборка 1 fps) | 0.57 / 0.48 |
| 170.91–177.51 с | открытая часть `WING_SHADOWED_TOWN` | ×1 | 67 | 0.53 / 0.51 |
| 178.11–183.41 с | вход в Окурово, тот же уровень | ×3 | 54 | 0.83 / 0.62 |

Последние две строки — отдельный прогон до исправления численной нестабильности NCC.
Повтор с исправленным NCC при выборке 1 fps также нашёл `wing` ×1 на 172–177 с и ×3 на
183 с. Полный повтор 10 fps после исправления был остановлен; результаты разных прогонов
не объединяются в общую оценку покрытия.

**Ограничение: примерно 110–170 с не сопровождаются устойчиво.** В разреженном прогоне
после 109 с совпадение ослабло, в 114 с трекер объявил потерю; до 172 с захват не восстановился.
Даже лучший отвергнутый поиск имел пик 0.496 при пороге 0.50. Причина потери и возможный
переход уровня не установлены; успех выбора нужного уровня в начале не доказывает работу
всех подземных переходов. Нужны разбор проблемных кадров, маски игровых значков и проверка
эталонов, а не простое снижение порога. При редкой выборке `lost-after=5` означает пять секунд,
поэтому точное время объявления потери здесь не сравнивается с прогоном 10 fps.

- На первом участке (0–66 с, исправленный NCC) из 323 кадров с видимой миникартой 322 дали
  позицию, один — слабое совпадение. На лугах максимальный шаг между соседними оценками —
  3.12 ед.; максимальная скорость по секундному окну — 15.6 ед./с. Равнина с небольшим числом
  деталей пригодна для сопровождения, но это не проверка полностью однотонной воды.
- Проверка SIFT раз в секунду на этом участке: 30 из 30 кадров локализованы; расхождение
  с NCC: ×1 — медиана 0.29, максимум 0.48 ед.; ×3 — медиана 0.48, максимум 1.29 ед.
  Это согласованность двух методов по одному эталону, **не независимая абсолютная точность**.
  Медиана масштаба SIFT — 0.5621 и 1.6886 px/ед. при ожидаемых 0.5625 и 1.6875.
- Для подземного ×2 в повторе с выборкой 1 fps: 14 проверок SIFT с координатами,
  расхождение с NCC — медиана 0.25, максимум 0.39 ед.; медиана масштаба 1.1216 px/ед.
  против ожидаемых 1.1250. Это подтверждает режим ×2, но погрешность больше, чем у ×1/×3;
  нельзя утверждать точное совпадение масштаба на всех уровнях.
- После телепорта к статуе первая оценка оказалась в 4.0 ед. от точки Kongying.
- Плавное изменение масштаба ×1→×3 за ~0.63 с измерено отдельно `zoom_probe.py` на каждом кадре;
  оно не должно интерпретироваться как посещение промежуточного режима ×2.
- Большая карта в кадрах 16 и 41 с: 1327 и 1959 RANSAC-inliers, масштаб ~0.50 px/ед.
  Кадр 62 с с выбранным уровнем и боковой панелью: 1023 inliers, ~0.5011 px/ед.
  В паре «последняя миникарта → большая карта в 16 с» позиции различаются на 7.7 ед.
  (~3.8 экранного px); стрелка на большой карте измерена по цветовому пятну.
- При отсутствии нужного эталона старые пороги принимали ложные уровни: пики 0.44 и 0.40,
  затем сопровождение с корреляцией 0.30–0.38. Нельзя трактовать любой найденный пик как позицию.
  Дополнительно найден и исправлен артефакт нормировки NCC на однотонной подложке уровней.

**Производительность офлайн на SM-S938B, Python + OpenCV, без игры.** В повторном прогоне
0–66 с шаг сопровождения (три масштаба текущего эталона, альтернативы раз в три кадра):
медиана 115 мс, p95 219 мс. Поиск по всем девяти локальным эталонам и трём масштабам:
медиана 11.5 с всего по двум поискам. Проверочный SIFT и декодирование видео не входят
во время шага. Это ещё не бюджет для оверлея: нужны C++-ядро, кэширование, ограничение кандидатов
и замер захвата/нагрева/FPS одновременно с игрой.
